# 按字段或全部范围下载合同文件到指定目录

用户要求下载指定字段、文件分类或合同全部文件时使用。由 Agent 编排现有 CLI 命令：查询合同详情 → 按用户指定范围收集文件 → 按文件 ID 去重 → 逐个获取临时 URL 并下载。全部文件范围还需查询各流程的审批附件及评论树附件。没有独立的批量下载命令。

## 0. 确定字段范围

以下路径相对于合同详情的 `data.contract`。先选择用户要求的字段，再收集该字段涵盖的全部文件；不要凭文件名猜分类，也不要将指定字段下载扩大为全部文件下载。

| 用户要求 | 对应文件范围 |
| --- | --- |
| 归档文件／归档合同文件 | 当前合同的归档主文件 + `contract_files.contract_archive_attachments[]`，主文件归属核对见下文 |
| 归档合同主文件／归档主合同文件／归档主文件／归档扫描件 | `contract_files.contract_scans[]` 中属于当前合同的归档主文件，不无条件选整个数组 |
| 归档合同附件／归档附件 | `contract_files.contract_archive_attachments[]` |
| 合同主文件／合同正文／合同文本 | `contract_files.contract_text`（单个对象） |
| 合同附件（页面字段） | `contract_files.contract_causes[]` |
| 其他附件（页面字段） | `contract_files.contract_attachments[]` |
| 盖章节点比对文件／盖章节点对比文件／OCR 比对文件 | `contract_files.contract_ocr_comparisons[]`；用户指定盖章节点时按该项 `node_id`、`node_name` 筛选，仅下载该节点涵盖的文件 |
| 某个自定义字段的附件，例如“付款凭证”字段 | 解析 `form`，定位该附件字段，收集其 `attribute_value[]` 中的文件，包含用户指定范围内的明细行和嵌套字段 |

- 完成字段范围及合同归属筛选后，字段中多个文件全部收集，不能只取第一项或自行选择“最新”文件。用户限定文件名、版本或明细行时，在对应字段内进一步筛选；无法确定时展示候选并确认。
- 自定义字段通过展示名、稳定字段标识、模块及明细行位置定位；同名字段无法区分时先确认。`contract_form_attachments[]` 和 `contract_template_custom_attachments[]` 是汇总分类，不能用整个汇总分类代替某个具体字段，也不能凭同名文件认定字段归属。
- 用户未指明哪个自定义字段，且没有明确要求全部时，列出可见附件字段供确认；明确要求全部自定义字段附件时遍历所有已识别的附件字段，并结合汇总分类去重。
- 所选字段已确认存在且值为空时，报告该字段无文件；字段缺失、不可见或结构无法解析时，报告无法确认，不以正文或其他分类补位。
- 仅下载上述合同字段时，跳过第 2 节流程查询，按第 3、4 节处理选中项。明确要求合同全部文件时，执行第 1、2 节的完整收集；单独指定审批或评论附件时只查询对应来源。
- 在选中范围内按 `file_id` 去重并保留所有来源字段；最终逐项返回实际来源。“归档文件”的结果应区分归档主文件与归档附件，成功数量只统计本次选中范围。
- 展示名称应与页面一致：`contract_causes` 虽然有“签订依据”的历史名称，页面对应“合同附件”；`contract_attachments` 对应“其他附件”。不能按英文名直译，也不能将这两类输出成“签订依据／普通附件”。“普通附件”等非明确字段名如有歧义，先确认用户指哪一类。
- 页面允许配置附件字段名。若返回字段元信息，按稳定标识 `contract_cause`、`contract_attachment` 对应展示名，再映射到上述文件分类，不把改名后的基础字段当成新自定义附件字段。自定义字段同样按标识、模块和位置定位，不仅按名称匹配。
- 盖章节点比对文件与“盖章节点的审批意见上传附件”属于不同来源：前者取 `contract_ocr_comparisons[]`，后者取对应流程任务的 `attachments[]`，不能互相替代。节点名称重复时通过流程、节点 ID 确认范围，不能仅凭文件名匹配。
- `contract_text` 在变更业务中展示为“补充协议”，在终止业务中展示为“终止协议”。沿用实际业务名称；用户要求原合同主文件时，先定位原合同，不能用当前补充/终止协议代替。
- 前端归档主文件按 `scan.businessId === contractId` 选择当前合同扫描件；合同变更场景可能含历史扫描件。当前开放接口存在未过滤列表覆盖已过滤扫描件列表的风险，且文件对象不含 `business_id`。若响应或其他已获授权的详情信息无法确认当前合同归属，应说明接口信息不足并列出候选供确认，不能按第一项、文件名或 `scan_type_code` 猜测，也不能把全部扫描件当作当前页面主文件。用户明确要求所有历史版本时，按该范围处理。

## 1. 读取合同和文件字段

沿用用户指定的 profile，全程使用同一 user 身份。名称或编号不能唯一定位合同时先展示候选；确定合同 ID 后执行：

```bash
contract-cli contract get <contract-id> --profile <profile> --as user --output json
```

确认命令成功及业务响应成功后，读取 `data.contract`；下表路径相对于该对象。ID 使用无损 JSON 解析并保留为字符串，不经过 JavaScript Number 等浮点数转换。

| 文件来源 | 文件项路径 |
| --- | --- |
| 合同主文件／正文 | `contract_files.contract_text`（对象，不是数组） |
| 合同附件 | `contract_files.contract_causes[]` |
| 其他附件 | `contract_files.contract_attachments[]` |
| 归档合同主文件／扫描件 | `contract_files.contract_scans[]` |
| 归档合同附件 | `contract_files.contract_archive_attachments[]` |
| 表单自定义附件 | `contract_files.contract_form_attachments[]` |
| 模板自定义附件 | `contract_files.contract_template_custom_attachments[]` |
| 盖章节点比对文件 | `contract_files.contract_ocr_comparisons[]` |

这些文件项使用 `file_id`、`file_name`；大小和 MIME 可作为参考。收集候选不代表已通过下载权限校验。不要使用详情里的旧 `download_url`，后续统一通过下载接口取得新地址。

`form` 是 JSON 字符串，先解析，再遍历字段及明细行。文件字段的 `attribute_value[]` 包含 `file_id`、`file_name` 等信息；结合 `attribute_type` 和实际字段结构确认文件值，保留字段名称、模块和行定位。多文件必须逐项收集，不能只取第一项；不要把任意 `id`、字段配置 ID、合同 ID 或 URL 当成文件 ID。嵌套对象/数组按实际结构遍历，不假设所有字段都在顶层；未知字段类型或无法解析的内容记录为清单不完整，不猜测字段值。

## 2. 收集流程与评论附件

仅在用户要求全部文件或指定审批/评论附件时执行；按第 0 节确定查询范围。

收集 `process_instance_ids[]`，并合入非空的 `process_instance_id`，按流程 ID 去重。后者是单个字符串；只有当前流程时只查询一次。不要用 `task_instance_id` 替代流程 ID，也不要为寻找流程枚举 ID。

对每个流程执行以下两个读取命令，不加任务过滤，以免遗漏附件；一个读取失败仍继续其他可执行的读取：

```bash
contract-cli contract approval get <process-instance-id> --profile <profile> --as user --output json
contract-cli contract approval comment list <process-instance-id> --profile <profile> --as user --output json
```

- 流程附件：读取 `data.process_instance.task_instance_list[].attachments[]` 中的文件项，收集 `file_id`；检查 `data.process_instance.complete` 和 `limitations`。
- 评论附件：从 `data.items[]` 开始，收集每层 `attachments[]`，递归遍历 `replies[]`，包括深层回复。评论接口不分页。`available=false` 的附件记录为不可用；不要因为父评论已删除就停止遍历其回复。
- 若响应给出所属合同 ID，核对其与目标合同一致；不一致的来源停止处理并记录原因，不擅自切换合同 ID 下载。
- 历史流程能查询到附件，不保证文件仍属于当前可下载集合；仍以统一下载接口的结果为准。拒绝时记为失败，不绕过校验获取存储地址。
- 按下面的来源展示规则输出，不将附件统称“流程附件”。同时保留流程 ID、任务 ID、节点 ID、评论 ID 或字段标识等定位信息，缺少证据时明确未确认，不凭文件名归类。

### 来源展示规则

| 实际来源 | 结果中的“来源”列 |
| --- | --- |
| 盖章任务 `attachments[]` | `盖章节点{盖章节点名称} -审批意见-上传附件` |
| 普通审批任务 `attachments[]` | `审批节点{审批节点名称} -审批意见-上传附件` |
| 归档任务 `attachments[]` | `归档节点{归档节点名称} -审批意见-上传附件` |
| 评论或任意层级回复的 `attachments[]` | `评论附件` |
| `contract_ocr_comparisons[]` | `盖章节点{盖章节点名称} -比对文件` |
| 自定义字段附件 | 对应的实际字段展示名；同名时补充模块或明细行位置 |

花括号中的名称替换为文件所属节点的实际名称；“审批意见-上传附件”是固定的位置描述，不需要把意见正文拼入来源。来源取包含该文件的任务项，不取流程当前节点。任务 `node_name` 为多语言对象时优先选用户语言（中文用 `zh`），缺失时使用实际可用语言，禁止直接输出对象或自行起名。比对文件自身的 `node_name` 为字符串。

当前任务 DTO 没有独立节点类型字段。可使用已确认的流程节点元信息；或按后端 `BpmUtil.getNodeType` 的编码规则解析 `node_id`：以冒号分成两段，取第二段首个下划线前的整数，`1` 为审批、`2` 为盖章、`3` 为归档。格式不匹配或其他类型时不强行套用三类标签，写 `节点{实际名称或节点ID}（类型未确认） -审批意见-上传附件` 并标明限制。不能将 `command_type`（动作）或 `task_type`（待办/已办/知会）当作节点类型，也不能按名称包含“盖章”等字样猜类型。

评论附件的来源列固定为“评论附件”，包括回复中的附件；流程和评论定位另存为明细信息，不改写该来源标签。同一文件 ID 出现在多个节点或评论中时只下载一次，保留所有不同来源及其定位，不能让第一次出现的来源覆盖其他来源。

## 3. 去重并准备保存路径

为每项保存合同 ID、文件 ID、原始文件名、所有来源（分类/字段/流程/评论）及处理状态。在当前合同内按字符串 `file_id` 去重，合并来源，每个文件只下载一次；多个合同分别处理，不跨合同混用文件 ID。不要按文件名去重。一个来源标记不可用但其他来源仍可用时，可对该 ID 调用一次统一下载接口，最终以服务端判断为准。

使用用户指定目录；未给出目录且需要批量本地保存时，先询问保存目录。构造完整文件路径传给 `--output-file`，不能把目录直接当文件路径。可创建指定目录中缺失的子目录。

一次下载多个合同时，默认在用户指定的根目录下按合同创建子目录，命名为 `<合同名称>_<合同编号>_<合同ID>`；缺少名称或编号时省略缺失项，至少保留合同 ID。目录名称同样按下面的安全规则处理，清理后仍须能通过合同 ID 区分，所有路径保持在根目录内。用户明确指定各合同目录时沿用其安排。单合同保留原有目录行为，不额外增加层级。

只取文件名的安全末段，替换路径分隔符、控制字符及目标系统不允许的字符，拒绝 `.`/`..`，确保结果仍在指定目录内。缺少名称时使用 `file-<file_id>`，不猜扩展名。同名不同 ID 在扩展名前追加文件 ID；仍与已有文件冲突时继续添加序号。默认不使用 `--force`，已有文件不能仅凭名称视为本次已下载。

## 4. 逐个下载与汇总

```bash
contract-cli contract download-file <file-id> --contract <contract-id> --profile <profile> --as user --output-file <完整保存路径>
```

CLI 自动获取 300 秒有效的临时 URL，再请求文件流，先写同目录临时文件并校验，完成后才落到目标路径。不要自行把下载元数据当文件保存，也不要用 `--raw > 文件` 实现批量保存，否则无法享受 CLI 的临时文件保护。成功提示是文本，不要按 JSON 解析下载命令 stdout。

每项检查退出码；成功后确认目标文件存在并读取实际字节数。记录成功、失败或跳过及原因，单文件失败继续剩余项。认证失效时暂停后续依赖授权的调用，保留已完成结果并提示重新授权。权限/参数错误不盲目重试；临时网络失败可重新调用下载命令至多一次以取得新 URL，不能重新下载已成功项。不输出或写入报告任何临时 URL、Token 或 Cookie。

最终默认使用 Markdown 表格展示下载结果，不使用逐文件项目符号列表。先写合同标识、保存目录及去重后的候选数、成功数、失败数、跳过数，再列以下列：

| 文件名（点击打开） | 来源 | 大小（B） |
| --- | --- | ---: |

下载汇总的第一行固定展示总统计，位于所有合同名称、编号和文件表格之前：`本次共处理 X 个合同，Y 个文件，成功 A 个，失败 B 个，跳过 C 个。` 单合同同样使用此格式。全部来源查询成功且清单完整时，Y 为去重后的文件总数；详情或来源查询失败、清单不完整时改写为“本次共处理 X 个合同，已发现 Y 个文件，成功 A 个，失败 B 个，跳过 C 个；文件清单不完整。” X 为本次请求处理的合同数，A/B/C 为文件下载数量，不能把合同查询失败计为一个文件下载失败。总统计下方再给出详情查询成功/失败数（有失败时明确列出）及保存根目录。文件总数按 `(contract_id, file_id)` 计数，即同一文件 ID 出现在不同合同时分别计入对应合同。详情或来源查询失败时，文件总数标为“已发现”，说明哪些合同清单不完整，不能把未能查询的合同当成零文件成功项。

随后按用户指定顺序（未指定时沿用查询结果顺序）逐合同分组，每个合同单独一张上述文件表。每个合同分组在表格前单独一行展示 `**<实际合同名称>**（合同编号：<实际合同编号>）`：仅实际合同名称加粗，不展示“合同名称：”标签，合同编号紧接名称后放在括号内，编号不加粗、不另起一行。单合同下载也采用此格式。 多合同下载时，每个合同标题前按展示顺序添加从 1 开始的连续序号，例如 `**1. 实际合同名称**（合同编号：实际合同编号）`；查询失败或无文件的合同也占一个序号，单合同不加序号。缺失值写“未返回”，不得用合同 ID 冒充合同编号；名称或编号缺失、重名或需要区分合同时另行补充合同 ID。组内给出该合同保存子目录、候选数和成功/失败/跳过数。相邻合同分组之间使用独立一行的 Markdown 水平分隔线 `---`，分隔线上下各留一个空行；上一个合同的表格及补充说明结束后再插入分隔线，下一个合同从加粗的实际合同名称开始。合同信息行与文件表格之间也留一个空行，避免内容紧贴。即使合同同名也不合并。没有可展示文件的合同保留该组，明确“查询成功且范围内无文件”或具体查询失败/完整性未知原因，不虚构文件行。各组分别说明清单完整性；总状态不能用其中一个合同的成功覆盖其他合同的失败。

表格只展示成功下载的文件，仅保留文件名、来源、大小（B）三列，不增加状态、文件 ID 或备注列。每个去重后的成功文件一行，使用实际文件名，不以文件 ID 或“文件”替代名称；文件名必须链接到当前宿主支持的本地文件交付地址，基于实际绝对保存路径生成，无本地链接能力时在表格下方说明保存路径。禁止把临时下载 URL 放入表格。大小使用下载后的实际字节数，未知时写“—”，不能写成 0。

失败/跳过项在对应合同表格下方单独列出文件名、来源及原因，不混入成功文件表、不生成成功文件链接。仍在汇总中统计成功、失败、跳过数量。同名不同 ID 的成功文件分行保留并指向各自文件，可在展示名称后加“（1）”“（2）”区分，不改变原始文件名；必要的同名或多来源说明放在表格下方。同一 ID 的所有不同来源合并在来源单元格中，节点类型和实际节点名称按上文规则完整显示。文件名、来源中的竖线、换行等按 Markdown 表格语法转义或转换，避免错列。文件 ID 及流程、任务、评论等定位信息保留在内部处理记录中用于去重和追踪，不默认展示给用户。

全部查询成功、结构已解析且每项均下载成功时，才能说“本次查询范围内的文件全部下载完成”。任一流程 `complete=false`、来源查询失败、字段缺失或结构未知时，说明已下载哪些文件以及清单完整性未知；不要将缺失字段等同于空集合，也不要把“没有发现”写成“没有文件”。

本流程使用现有临时 URL 下载契约，不承诺下载时重新解析最新版本或额外水印处理。文件是否可下载最终由服务端决定。

存在失败或未下载项时，标题写“部分下载成功（成功数/候选数）”，不得只写“下载完成”。`110125` 表示文件不存在或不可见，不能仅凭错误码断定账号权限不足或承诺换高权限账号即可解决。清单完整性、流程状态和下载成功率分别报告；流程 `complete` 不代表流程已完结，也不能证明文件全部可下载。
