# 引导式澄清

仅在用户意图会对应不同查询结果时使用本参考。显式关键词意图直接走页面默认“全部”关键词；明确的业务角色或字段直接映射到 [主 Skill 场景](../SKILL.md)。没有显式关键词意图、但可合理推测是人员、部门、交易方、我方主体或自定义字段时，Agent 先查候选或字段元数据，只对仍影响结果的业务含义进行引导确认。

## 如何提问

把条件说成“业务字段＋匹配方式＋值”，例如“申请人姓名包含张三”“合同文本包含里斯”“项目区域为华东”。关键词查询不能复述为精确相等，姓名关键词不能复述为已锁定唯一人员。

- 已有上下文支持某种理解，但用户表达仍有关键缺口时，用确认句补齐：“你指的是『项目区域为华东』的合同吗？已归档这个条件会保留。”
- 存在多个同样合理的解释时，用选择句：“这里的区域指『项目区域』还是『交易方所在区域』？”选项必须来自实际元数据或已明确的业务概念，不能把示例字段当作当前租户真实字段。
- 元数据只返回一个相近名称，不一定代表已确定用户意图。用户说记不清字段名、或业务含义仍不明确时，展示该真实候选供确认；用户已明确字段且元数据唯一对应时直接查询。
- 没有候选依据时，直接问缺失含义：“你说的『华东』是哪个字段的值？可以告诉我页面上的字段名称。”不要凭值猜字段，也不要求用户提供字段 key、ID 或 JSON。
- 一次集中询问影响请求的关键缺口；已有答案和上下文能够确定的条件不重复询问。用户无需了解 CLI 参数。
- “关键词搜索”“页面搜索框”“全部搜索”是显式关键词信号，优先于姓名、部门或公司外观。“搜索/搜一下 X”只给普通搜索词时也默认使用页面关键词；“X 的合同”等关系表达可以触发实体推测。候选查询没有可靠命中时，不继续猜角色，改用页面默认关键词并说明范围。

## 用户怎么说 → 应该怎么引导 → 确认后怎么查

下表中的元数据是说明前提，实际执行须读取当前身份的真实响应，不能预设存在这些自定义字段或选项。

| 用户怎么说 | 已有依据与应该怎么引导 | 确认后怎么查 |
| --- | --- | --- |
| “需求人张洋，再加交易方湖南安克电子科技有限公司。”且截图已选中主体。 | 保留已确认需求人，主体选择含义明确，不再询问是否同时满足；Agent 复用主体 ID 或按名称查交易方候选。有同名主体且上下文无法区分时才补业务信息。 | 按 [组合配方](trading-party.md) 增加交易方 ID/MUST，清除旧分页；不能悄悄换成名称关键词或丢掉需求人。 |
| “关键词搜索毛鹏”，且截图选中“全部”。 | 查询范围已有截图依据，直接执行，不要求用户选择人员或先给 user_id。 | 用 [全部关键词配方](all-keyword-search.md)，说明是多字段关键词匹配，不称为“毛鹏申请的合同”。 |
| “搜索毛鹏”。 | 只有普通搜索词，没有业务角色；即使能查到同名人员，也不先打断用户。 | 使用页面默认全部关键词并说明范围；用户随后说“限定申请人”时再查人员候选并重构请求。 |
| “毛鹏的合同”。 | 没有显式关键词意图，但关系表达可推测为人员。Agent 先查人员候选；有可靠候选时询问是申请人、需求人等角色，还是页面默认关键词。同名时同时展示可区分的业务信息。 | 用户确认角色后走对应 ID 筛选；选择关键词或候选证据不足时走页面默认全部关键词。 |
| “查张三申请的合同。” | 申请人角色明确，Agent 先复用可靠 user_id 或通过人员查询解析候选；有重名才澄清具体身份，不让用户找 ID。 | 优先 `CONTRACT_SUBMIT_ID` 精确筛选，不默认降级成姓名关键词。 |
| “按申请人姓名关键词张三查询。” | 用户明确要姓名关键词，不必先确认唯一人员。 | 使用场景 6；说明按姓名关键词匹配，不能称为唯一人员。 |
| “合同需求人是张洋的合同。” | 需求人角色已明确，不再问是不是申请人。优先复用同身份已确认 ID，缺少时通过 employee list 查询姓名候选；同名或多需求人无法对应时，只补充身份依据。 | 按 [需求人配方](demand-person.md) 使用真实外部 user_id；不改用申请人姓名，也不把姓名塞进需求人 ID 数组。 |
| “查范学冬申请、变更中的合同。” | 优先复用已确认人员 ID 或查询人员候选，保留状态；仅在用户明确要求姓名关键词时采用名称路径。 | 申请人 ID/MUST＋combine 状态字符串 `"10"`；两种已验证路径见 [完整配方](applicant-status.md)，按组与实际状态报告结果。 |
| “全部关键词搜毛鹏，并限定某申请人。” | 两个条件都已明确时，不重复问是否 AND；先复用同身份已有确认 ID，或通过 employee list 取得该申请人的可靠候选，姓名文字与截图不一致或出现同名时，只确认具体人员。 | 保留十二字段关键词，申请人按真实外部 ID 构造 filter；不把姓名 MUST 追加到关键词数组，也不要求用户填写技术 ID。组合验证见 [申请人说明](search-combinations.md#申请人姓名与全部关键词直接并列不能保证-and)。 |
| “查张三的合同。” | 没有显式关键词意图，但关系表达可推测为人员。先查候选，有可靠候选再问：“你想按『全部』关键词搜索张三，还是限定张三作为申请人等角色？”不能自行改成申请人或“我的合同”。 | 选择全部关键词时用十二字段配方；指定申请人优先 ID 筛选；候选证据不足时也回到页面默认关键词。 |
| “搜索里斯。”或“关键词搜毛鹏”，未指定字段。 | 已明确是关键词查询，默认全部关键词并说明范围，不先强制用户挑一个字段。 | 十二字段同词 OR；用户进一步指定文本、申请人等范围后，按对应分支重构并清除旧 token。 |
| “查合同申请日期在 9 月 15 日到 16 日的合同。” | 字段明确；已有年份与业务时区时直接查询，缺少时只补充缺口。不要再问这是提交时间还是创建时间。 | 按 [申请日期说明](submission-date.md) 写 combine 日期路径；未要求状态时不添加已归档条件。 |
| 前文已在讨论项目区域，用户补充“查华东那些，已归档的。” | 如果前文已经明确华东是项目区域的值，直接查；仅讨论过该字段但仍可能指其他含义时，问：“你要查的是『项目区域为华东』且『已归档』的合同吗？” | 读取项目区域元数据，解析实际值，保留归档状态，再构造完整请求。 |
| “查区域是华东的合同。” | 先按展示名“区域”发现字段；假设实际返回项目区域、交易方所在区域，且上下文无法区分，问：“这里的区域指『项目区域』还是『交易方所在区域』？” | 只使用用户选定字段的 key、类型和候选值；不能并列两个字段扩大匹配。 |
| “项目区域为华东”。 | 字段和值都明确，直接按“项目区域”发现元数据；唯一且业务含义一致时不追加确认。 | 按真实字段 key、类型和候选值查询；多个合理字段时才引导选择。 |
| “查区域为华东的合同，字段全名我记不清了。” | 按“区域”发现字段；即使只返回“项目区域”，仍问：“你要查的是『项目区域为华东』的合同吗？” | 用户确认业务含义后，使用该字段真实元数据构造请求。 |
| “查华东”。 | 只有普通搜索词，没有字段或实体依据，不把“华东”猜成自定义字段值，也不阻塞查询。 | 使用页面默认全部关键词；用户随后明确“项目区域”时再查询字段元数据并重构请求。 |
| “区域改成华南，其他不变。” | 已查询“项目区域为华东且已归档”，当前在第 2 页。字段角色清楚，直接继续。 | 按原字段元数据解析华南，替换区域值，保留已归档及其他条件，清除旧 token 从第一页查。 |

自定义字段如出现同名选项、区间边界或日期角色的歧义，同样只问影响业务含义的部分；如果元数据已明确编码或边界，Agent 自行转换，不把它变成用户要回答的技术问题。

## 澄清后的执行边界

- 保留已确认的字段、匹配方式、值、范围和条件关系，选择主 Skill 的对应 JSON 配方；模板占位值必须替换为真实元数据，示例不得原样调用。
- 回复“是”只确认刚才复述的业务含义；回复某个候选只解决该处歧义。仍有必需信息缺失时继续核实，不据此删除其他条件或扩大搜索范围。
- “再加一个条件”是与既有条件同时成立；“改成”是替换相应条件。若“华东、华南都要”等说法无法判断是任选其一还是同时满足，再澄清关系，不机械映射为 AND 或 OR。
- 业务意图明确但接口组合能力不确定时，由 Agent 核实参数契约。比如用户要求“姓名包含张三，同时正文包含里斯”，不能仅通过询问“两个都要满足吗？”就宣称请求已经支持 AND；无法可靠表达时说明具体限制，不发送放宽后的请求。
- 新增、替换或删除条件，以及改变排序或范围后重新查第一页；只有明确继续同一查询时才复用返回的分页 token。业务成功、空结果和后续页判断仍遵守主 Skill。
