# 合同交接

开始前读取 [API 契约](references/api-contract.yaml)。业务输入、调用参数、依赖、接口证据和执行门禁以该契约为准；不能凭本文中的流程描述补造接口。

## 输入与执行资格

接受合同编号、名称、合同链接、一组明确对象或完整搜索条件，以及一名接收人。名称重名、编号不精确或接收人不唯一时，用编号、部门等必要信息消歧，不默认第一条。不让用户手抄内部 ID。

本期优先验证指定一份／多份普通合同交接；合同组为灰度扩展，已有结果保留，不作为核心验收的前提。系统识别业务类型和组关系，不要求用户选择“普通／不普通”。全部搜索结果及合同组仍遵守各自的完整性要求，以下规则不意味着所有场景目前均可运行。

- `readiness.contract_complete` 不是 true 或 `delivery_status` 为空：禁止正常业务执行，不宣称达到正式发布或业务启用条件；可作为开发集成候选交付。允许证据支持的只读发现，以及契约 `business.development_validation` 允许且用户明确确认专门 test 清单的受控交接。指定普通合同可使用下述“普通合同核心测试”范围；其他场景仍须完整影响预检。全包缺口与该场景测试结果分别记录，不自动升级成熟度。
- `RECIPE_READY`：配方完整但运行证据不足；可开展已明确授权的 test 验证，不能当作正式可运行能力。
- `RUNNABLE`：仅在已验证环境和允许通道上执行，且该通道覆盖本场景全部必需调用，包括结果回查。某个只读接口成功不能代替整个交接流程通过。
- 无法查全搜索结果或展开合同组成员时，不执行对应的全选／整组场景。普通合同核心测试按下述说明关联影响，不能把未知影响解释为没有影响；指定对象、接收人不明确或没有可靠回读路径时仍须停止。

### 普通合同核心测试

仅用于 `test` 环境中用户指定的普通测试合同（单份或多份固定入口），按契约 `business.ordinary_core_test` 执行。先读取身份、权限、唯一接收人及合同详情，核对真实类型、状态、当前归属人／申请人和 `assemblyId`；真实合同组及其成员不走此分支。有来源明确的 ID 时直接读取，不为单份测试全租户搜索。

写接口自行展开同 `groupId` 的有效关联记录，并按现有规则处理相关草稿。完整关联清单、灰度配置、BPM owner、旧授权停用和通知日志不作为这个核心测试的额外前置查询。将已知关联说明给用户；未完整枚举的范围如实标记未知，不声称所选合同是唯一实际影响对象。若用户明确要求“其他任何合同／草稿都不变”，现有接口无法保证时停止，不能用此分支扩大其授权。

一次确认中列出指定测试合同、接收人、预期双角色变化，并说明：“接口可能联动同组关联记录，并按系统规则处理相关草稿；本次核验指定合同的交接结果。”用户确认这份清单与处理方式后，写前复查关键字段，调用原同步交接接口一次，再回读指定合同。不给接口增加验收模式、灰度或角色选择参数。

该分支保存 `scope_mode=ORDINARY_SELECTED_ENTRIES`、`impact_complete=false` 和 `result_scope=SELECTED_ENTRIES_ONLY`；确认清单冻结的是指定入口，不伪造全量关联资源清单。以本次授权／新增交接记录及归属人、申请人回读判定指定合同结果。部门、需求人及流程／通知可随已有数据单独说明，缺少其独立证据不阻塞本次核心验收。不能据此宣布全量关联、副作用或整包已通过。

## 通道与授权

读取契约的 `runtime.execution_mode`。HYBRID 按 MCP、CLI 顺序检查；MCP_ONLY 只检查 MCP；CLI_ONLY 只检查 CLI。检查实际 Tool Schema 或 CLI 命令帮助，确认支持通用 Open Web 调用。仅入口缺失或能力不兼容时才按模式换通道；业务拒绝或已发送请求不能通过换通道重放。

使用相同 test 用户授权上下文。MCP 只映射其真实 schema 支持的 method、path、query、body/raw_body；CLI 使用已验证的 `api call --channel web`，显式沿用选定的 profile 和 user 身份。配套 CLI 与全局同名命令可能版本不同，不能只看命令名。业务请求只能访问契约中确认的 `/open-web/web/**` 路径。

无通道时按契约的安装／连接恢复策略处理；来源必须经批准，安装变化须说明。授权失效时沿用通道自有登录流程，授权后续办原请求。Skill 不接收、构造或保存 token、Cookie、可信身份头，不切换到生产，不借用其他用户身份。具体安装路径、profile 和账号属于本机运行上下文，不硬编码进业务配方。

JSON 长整型 ID 全程无损处理；内部 `employeeId` 与开放 `user_id` 不可混用。MCP 必须保真时用 `raw_body`，CLI 使用受控 UTF-8 输入文件，避免脚本数值精度或 shell 展开改变请求。

## 1. 查全并固定目标

按搜索配方查找合同，保留用户的 tab、筛选字段和条件。合同名称、编号、默认全部关键词搜索不能互相替代。链接仅用于解析已确认格式的业务标识，不直接访问用户提供的任意地址执行操作。

指定合同编号时，使用 `search_contracts` 中的编号条件结构和完整请求示例，将用户编号填入筛选条件；逐条比对返回的 `contractNumber`，从精确匹配项取得真实合同 ID，不先发起无条件的全租户搜索。若已有来源明确的合同 ID，直接按对应业务类型读取详情。零条精确匹配不能直接证明合同不存在：草稿／协商等状态可能不在该搜索范围，需说明范围限制；没有已验证的替代查询配方时报告缺口。

搜索返回可能按组聚合：分别记录结果组、选中入口和实际合同资源，不把组总数当合同总数，也不把同组所有成员当作独立匹配条件的合同。分页必须使用接口真实分页语义，去重并检测遗漏或漂移。达到接口窗口限制或无法证明集合完整时，不报告“已查全”，不提交“全部”。

“全部符合条件”指本轮查全后经用户确认的固定集合，不调用动态异步全选交接接口，不自动纳入确认后新增的搜索结果。保留排除项；查全本身不是服务端事务快照，确认前仍要复核。

### 只读查询当前角色和交接历史

仅查询时不要求接收人或交接确认。普通处理资源按 `contract_detail` 读取创建人、当前归属人、当前申请人；按该配方的 `handover.records` 映射展示交接前人员、交接后人员、操作人及时间。合同组和已确认的成员按组配方读取其有填充保证的字段，不用普通详情作为强制通道；父组历史须标明所属对象，不能冒充成员独立历史。保留角色差异和空值，不以创建人代替当前归属人，不以操作人代替交接前人员，不用当前角色补齐历史字段。仅返回历史记录时，明确这是查询到的历史，不代表本次发生了交接；记录为空时只报告接口未返回记录，不承诺从未交接。

日常使用依据本包配方和实际响应完成查询；缺少参数或字段含义时说明具体缺口，不通过遍历用户目录、读取本地研发源码来补齐运行依赖。研发维护和验收修订可以另行核查源码，并将确认的信息补入配方后复测。

## 2. 预检与影响说明

读取当前操作者、功能权限、合同状态、业务类型、归属人、申请人、组与变更关系，以及接收人实际员工记录和部门。普通合同及父组按配方读取合同部门；组内子合同不要求读取或校验合同部门。能查看、能搜索、出现在“我的合同”或拥有全部交接权限，均不能独自证明某份合同一定能交接。

归属人在已分析的普通新建／草稿初始化路径中初始为创建人；自动完成单和历史副本等可能继承原归属人。交接时始终读取当前值，不用创建人代替当前归属人。

对非合同组处理分支，成功后的预期变化是：

| 交接前关系 | 成功后的变化 |
|---|---|
| 当前归属人与申请人相同 | 两者一起变更为接收人 |
| 当前归属人与申请人不同 | 只变更归属人，申请人保持原值 |

这是结果规则，不是授权条件。仅要求更换申请人时，不按合同交接执行；需求人列表、归属人和申请人是不同字段。合同组须按自身处理器和已验证配方判断，不能套用上表，不能利用合同组路径变相实现“仅交接申请人”。

第三方代交接由服务端实际权限及操作者关系决定。已分析的分支要求管理员交接标记成立且操作者既非归属人也非申请人；Agent 不提交提权标记，也不把有全部权限等同于一定进入第三方分支。

`groupId`、`assemblyId`、父子标识与变更链 ID 各有含义，不能互换；普通合同的 `groupId` 关联记录不等于灰度合同组功能。完整范围场景按已验证查询展开全部影响；普通核心测试按前述范围处理关联影响。组内子合同不能擅自独立提交。空前后链字段不证明没有同组资源，`checkDrafts` 返回首个草稿不证明完整影响清单。

已确认的组内子合同，按父组权限和组成员配方核对身份、状态、角色和需求人，不强制逐个调用普通合同详情。子合同部门由后端按现有交接规则处理，不作为 Skill 的预检、写前复查或交接结果校验项，也不为此增加查询。该字段缺失不阻塞交接、不降低交接结果状态；若响应包含部门空值，不据此推断未设置，也不以父组或员工部门补值。不用有业务更新副作用的聚合详情接口替代只读查询。

灰度、草稿与副作用按实际处理器及本次验收范围判断。普通核心测试由服务端处理配置和关联变化，不再要求客户端先证明所有底层副作用；其余场景沿用契约的完整范围规则。写前说明预期变化，实际准入和变更由服务端最终判定，不能把“尚未执行”当成必须先取得本次成功证据的门禁。必要身份、人员角色、指定范围或结果回查能力缺失仍阻止执行。

结合已验证的租户配置说明部门变化、关联草稿处置、协商／流程、提醒与通知。不能承诺所有审批待办都迁移、所有旧提醒都停止或原交接人必定失去查看权。Skill 负责必要预检和说明，接口按提交时状态最终校验和变更。

## 3. 确认与分批执行

形成可审阅的确认清单，至少包含：

- 选中入口的编号／名称及数量；完整范围场景另列实际影响资源及数量。普通核心测试只列已知影响，未知关联不填写总数。
- 接收人及用于消歧的部门；归属人、申请人的当前值和预期值。普通合同及父组按配方说明部门变化；子合同仅说明后端部门联动规则，无需列部门前后值。
- 关联草稿、组成员及其他已确认影响；排除对象与真实原因。

已有明确授权可以沿用到相同对象和影响；新范围、接收人变化或新增关联影响需要重新确认。混合批次只执行用户最终确认的可交接部分，不能静默排除后说全部成功。

固定确认清单后，每批最多 100 个选中入口，串行调用同步交接配方；100 是 Skill 的提交策略，不宣称是接口上限。普通核心测试首轮仅单批指定少量合同，不开展未知关联下的跨批自动续发；其余场景关联资源数量另计，整体操作的组不拆成子合同写入。每批写前核对关键状态，变化对象暂停并更新清单。

按契约生成 `manual`、`reason`、接收对象及资源参数。业务租户字段从实际接收人记录取得，不能用它伪造登录租户；禁止自填 `handoverByAdmin`。调用一次后保存请求关联标识和已确认清单用于核对，不保存凭证或不必要的个人信息。

## 4. 逐份核对与恢复

先检查通道、HTTP 和下游业务码，再核对本次授权记录、提交前快照与只读回查。CLI 若只返回下游 body，不能臆造外层 HTTP 状态；开发验证从通道已提供的日志取得 HTTP 证据，不自行绕过网关抓取。

返回整体成功、空记录或记录数量少于输入，都不能直接推出逐份结果。以真实资源 ID 和目标接收人关联本次执行证据；历史同资源记录、交接前已归属目标人或查询列表消失不构成本次新增成功。

| 状态 | 证据要求 |
|---|---|
| 成功 | 本次执行证据与实际归属人／申请人变化对应，相关核对项已完成。 |
| 跳过 | 有明确未执行证据；原因只写已知事实。 |
| 失败 | 接口或可靠回查明确该对象执行失败。 |
| 未执行 | 执行前排除、取消，或因前批停止尚未发送。 |
| 待核实 | 已发送但超时、响应缺失、字段矛盾、回查不可用或证据不足。 |

已完成部分与其他状态分列；指定对象存在待核实项时，不报告指定清单全部完成。原归属人与申请人不同时，专门核对申请人是否保持原值。普通核心测试明确报告“指定合同交接结果”，部门等观察项及未核实关联、副作用另列，不将其缺证混同为指定合同交接失败。组成员仍以父组本次记录、完整成员关系及逐成员角色回读核对。合同主记录成功不能推断流程、草稿或通知副作用全部成功。

合同组受控 test 可按契约中的具体方法，安排写后现有接口回读、飞书机器人消息人工观察及必要的授权服务日志补证。合同角色变更、BPM 服务响应／实际流程 owner、通知发送／送达分别记录；依据处理器顺序推断 BPM 成功路径时，必须标明未独立读取流程 owner。没有观察到消息保留通知待核实，不认定交接失败，也不要求写前先取得接收人账号。副作用证据未齐时不能宣称本次全项通过或升级整包成熟度。

写请求超时、断网、5xx 或结果不确定时，停止后续批次，先只读核对；不自动重试、不切换 CLI/MCP 重放、不交接回原人作为回滚。即使本批回查成功，也不能自动发送被停止的后续批次；先展示核对情况和剩余清单，等待续办指令。403/404、无查看权限、查询延迟不能单独证明成功或失败。

收到明确续办指令后，建立关联原批次的续办清单。原不确定资源保持“待核实”并排除；只有剩余资源完整预检通过、与不确定资源无共同影响对象、且接收人与影响未超出原确认时，才可作为新的受控执行批次继续。明确指向原清单的续办指令可以作为授权，不重复索要同一确认；范围或影响变化时再确认。用户要求重试原不确定资源时，仍须先核实其实际结果和重复执行条件，不能把“再试一次”当作安全重放证据。

## 输出与跨 Agent 交互

用简明表格展示合同编号／名称、执行状态、实际变化、原因及可用链接，汇总选中入口数、实际影响数和各状态数量。未知原因、无法读取的必需核对字段写明“待核实”，不补猜测；子合同部门不列为待核实事项。不得将返回 `success=true` 翻译为“全部交接完成”。

Codex 原生选项可用时使用，否则用编号候选；豆包和 WorkBuddy 同样保持消歧、确认范围与结果判据，授权按宿主既有流程。正文表格足够，不强依赖图表、二维码或某一种选项工具。当前首轮只验 Codex，其他 Agent 不继承通过状态。

## 验证与交付状态

开发和验收时读取 [业务验证清单](references/validation-cases.md)，运行 `ruby tests/validate_contract.rb`。测试脚本的自身回归、离线契约校验、真实业务测试分别记录，未执行的业务用例保持未测试。契约和所有必需回查配方都有证据后才能升级成熟度；仅修正文档或通过格式检查不升级业务状态。
