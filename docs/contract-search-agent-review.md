# 合同搜索：Agent 友好性与逻辑清晰度评估

日期：2026-09-20。范围：当前搜索 Skill、全部搜索参考、CLI help、字段发现与合同搜索实现、场景测试，以及必要的 MCP 契约/CLM 本地源码。此轮只分析，未修改搜索实现。

本文保留最初评估时的证据和问题。后续逐项实测、已落地修复与待验证范围见 [逐项验证记录](contract-search-validation.md)，不要把下文历史待办直接当作当前状态。

当前执行总纲及是否仍缺接口的最新判断见 [总纲与接口缺口复核](contract-search-guideline-review.md)。人员、部门候选命令现已补齐；以下早期“暂缓”结论不代表当前能力。

结论：已有“用户怎么说 → 应该怎么查 → 示例 JSON”结构可以保留；字段发现与搜索放在同一个 Skill 也是正确的。下一步应优先保证复杂条件、字段类型和执行结果的一致性，再减少 Agent 的阅读、猜测和重复确认。单项搜索可用，尚不能代表任意组合都可靠。

## 证据与验证范围

- 三个独立 Agent 分别评估自然语言场景、字段说明、组合语义。
- 本地临时 mock 测试复现旧 search 的业务错误未返回 error、请求数值变化、ID 类型参数无效；临时测试已删除，业务代码未改。
- 生产仅执行三次每页最多 5 条的只读对照，确认姓名 MUST 与正文 SHOULD 的实际组合行为。请求使用原有已授权生产 profile，未切换身份，未写入生产数据。
- 字段发现新命令的生产链路、定向测试、既有 lint/本地 mcp.yaml 问题沿用前轮证据；本轮没有为文档分析重复跑全库测试。
- 本地 CLM 源码仅用于解释及发现边界，不等于生产部署证明。下文明确区分线上实测、本地复现、源码线索和设计建议。

## 1. 最优先：建立可靠的组合规则

生产对照全部 code=0、success=true：

| 请求 | 本次条目数 | has_more |
| --- | --- | --- |
| 特制无匹配申请人姓名，单项 SHOULD | 0 | false |
| 正文包含“里斯”，单项 SHOULD | 5 | true |
| 同一无匹配姓名 MUST + 正文“里斯” SHOULD | 5 | true |

第三项的首页合同 ID 与第二项完全相同。此结果证明该请求中的姓名 MUST 没有产生预期的必需申请人限制；不是业务失败，也不能解释为“同时满足姓名和正文”。5 条只是本页数量。

本地源码线索：姓名和部门名称被解析成 ID 后强制改写为 SHOULD；无候选姓名条件可能被移除，其他条件继续执行。关键词进入一个扁平 bool，并设置 minimumShouldMatch(1)。见本地 CLM `ContractSearchService.java:1203/1220/1243/1267`、`GroupQuerySchemaBuilder.java:500`。

现有 [主 Skill](../skills/contract-cli-contract-search/SKILL.md) 已警告不能把 AND 改成 OR，但“先确认服务端语义”没有提供 Agent 可执行的解决路径。用户已经说清“同时满足”时，不应再要求用户解释接口如何表达 AND。

建议建立组合矩阵，并为每项标明验证层级：

| 用户需求 | 当前判断 | 下一步 |
| --- | --- | --- |
| 一个文本关键词，正文及附件任一来源命中 | 五来源 SHOULD；已生产验证 | 保留 |
| 一个文本关键词 + 金额/币种等结构化限制 | 本地源码支持关键词组与 filter MUST 组合 | 补边界与结果集联调 |
| 名称关键词 + 状态/日期 | 本地源码会把 combine_condition 转成额外 MUST | 补结果集联调，不能只校验 JSON |
| 姓名/部门名称 + 正文，要求同时满足 | 不能机械合并场景或仅把名称改 MUST | 确认可靠结构化 ID 筛选或服务端组合契约后再支持 |
| 文本同时包含两个词 | 两组五来源 OR 不能压成一个 SHOULD 数组 | 单独验证分组 AND 表达 |
| 批量编号 + 其他关键词 | 本地源码存在清空其他 condition_units 的分支 | 作为组合边界验证，暂不承诺全条件生效 |

人员/部门列表命令仍可暂缓，但理由应限定为“单项名称关键词已能直接查询”。精确身份、重名消歧和复杂组合是否需要候选能力，属于后续独立判断。

## 2. 场景引导：先给执行顺序，再展开示例

当前主文件 292 行，接口选择表在第 250 行，组织查询在第 265 行。主文件又要求读取 shared，shared 要求读取 auth；当前这三份文件共 714 行。已有授权的普通搜索也容易被大量无关说明分散注意力。

保留用户要求的三段式，不把全部场景移走。建议调整为：

1. 简短决策入口：用户意图、范围/身份、直接搜索或字段发现。
2. 执行顺序：识别字段角色 → 必要时发现元数据 → 构造并核对全部条件 → 查询 → 解释结果。
3. 场景索引与现有三段式示例。
4. 结果、追问和异常规则。
5. 具体字段契约通过参考链接按需读取。

主文件只保留搜索必需的授权上下文规则；明确当前任务可复用已有有效授权和已确认配置。完整授权流程按现有共享约定使用，避免把每轮查询误作一次新授权。

“帮我查一下合同”应有统一分支：没有范围/条件时只问一个短问题，或在用户明确说“列最近合同”时使用已说明的默认可见范围和排序。空请求在接口上合法，不等于用户一定要无条件列合同。

## 3. 场景覆盖：补组合与追问，少堆孤立例子

当前文本、正文金额、我的合同、编号、日期状态、申请人、部门、自定义字段、续页均有案例。主要缺口不是更多同类单字段示例，而是：

- 同时包含多个独立业务条件时，如何选择可靠组合路径。
- “刚才条件不变，再加金额”时，恢复完整请求、只修改新增条件、删除旧 page_token，从第一页重新查。
- “把审批中改成已归档”“取消部门条件”时，替换或删除目标条件，保留其他条件。
- “没有结果”后，先区分字段未匹配、业务失败、合同零命中、未查完；放宽条件需用户明确授权。
- 模糊姓名/部门、系统编号与同名自定义字段、需求部门与申请部门等歧义如何消除。

独立 Agent 模拟结果：

| 场景 | 结果 | 暴露的问题 |
| --- | --- | --- |
| 姓名 + 部门 + 文本 | 无法可靠构造 AND，停止 | 组合规则没有闭环；部门角色不够具体 |
| 日期 + 状态 + 自定义选项，提供唯一字段元数据夹具 | 能生成请求，但静态 label 规则与元数据 value 规则可能分歧 | 需要统一字段取值优先级 |
| 保留上一轮条件，追加金额严格大于 5000 人民币 | 能保留旧条件，但无法确认严格大于表达 | 范围边界与修改查询流程缺失 |
| “帮我查一下合同” | 选择澄清 | 需要统一模糊需求与默认列出之间的规则 |

## 4. 字段说明：从枚举清单改成可执行的字段契约

每类字段至少应能回答以下问题，动态字段以实际 MCP 元数据为准：

| 说明项 | 要解决的问题 |
| --- | --- |
| 业务角色与用户叫法 | 申请人、创建人、归属人、需求人是否混淆？ |
| 匹配方式 | 关键词、精确、枚举多选、范围分别是什么？ |
| 请求位置 | 顶层、combine_condition、condition_units 或 filter_units？ |
| 字段标识 | search_field、filter_unique_key 是否需要一起使用？ |
| 值类型与来源 | 字符串、数字、数组、状态 CSV；label/value/code/ID 从哪里取？ |
| 单位与边界 | 金额币种、日期时区、秒/毫秒、按天/按时刻、包含端点与否？ |
| 组合能力 | 本字段可与哪些条件可靠 AND/OR？ |
| 空值与失败 | value_scopes 为空、没有候选、业务失败时怎么办？ |

具体需要修正/补充的点：

1. **选项与币种存在类型冲突。** [user 参数第 177 行](../skills/contract-cli-contract-search/references/search-user-parameters.md#结构化筛选-filter_units) 将 CONTRACT_FORM_FIELDS_OPTION 只写为字符串/字符串数组和 label，第 181 行却说明同一枚举用于币种 code 数组。本地字段服务对应 CURRENCY_ID_ARRAY、整数数组。不能仅凭 search_field 选择 JSON 类型，也不能把实际元数据 value 无条件替换成展示 label。
2. **部门角色不足。** CONTRACT_DEPARTMENT_NAME 在本地源码中处理提交人部门；DEPARTMENT_AUTHORITY 查权限部门，两者不能视作名称/ID 的等价版本。还应区别需求部门、自定义部门。线上具体角色须与页面/MCP 进一步核对，不能仅凭现有同名结果断言。
3. **范围未写开闭边界。** 当前金额表只写两个端点。本地金额实现使用 gte/lte，即含端点；“大于 5000”不能直接翻译成 [5000,null]，也不能在未确认金额精度时擅自用 5000.01。
4. **日期缺少粒度说明。** 提交日期字符串与自定义日期毫秒数组不是同一契约；本地自定义日期实现会转换为 yyyy-MM-dd，不能因输入是毫秒就承诺小时级过滤。业务时区已确认时应复用，避免每次重复问。
5. **空候选不等于不可查询。** 自由文本的 value_scopes 为空是正常情况；枚举、人员或部门缺少必要候选才可能需要补充信息。

建议保留按业务类别分组的字段速查表：名称/编号、文本来源、人员/部门、状态/枚举、金额/币种、时间、动态表单。少见字段与 legacy 差异继续按需读附录。

## 5. 字段发现：补“响应到请求”的完整示例

[字段发现参考](../skills/contract-cli-contract-search/references/search-filter-fields.md) 已列出重要属性，但尚缺一个完整转换过程。建议补一个脱敏案例，明确：

1. 检查业务响应后，从 data.items[] 选择实际目标字段。
2. 结合字段业务含义与 field_type 区分同名系统/自定义字段；存在真实歧义才询问。
3. 读取 request_location/request_paths，以及 search_value_type、value_description、usage_hint。
4. 读取 examples[].request_fragment，结合真实候选替换业务值；示例值不是用户真实输入。
5. 将片段合并进现有完整请求；不能覆盖旧条件，也不能仅把片段直接当完整请求发送。
6. 对同一租户/身份、同一已确认字段，在后续追问中复用已验证元数据；遇失效或字段变化再刷新。

类型说明应把语义枚举和 JSON 形状分开解释，例如 TEXT、STATUS_CODE_CSV、MILLIS_RANGE_ARRAY、CURRENCY_ID_ARRAY；具体映射必须来自实际 MCP 返回。不能把 search_value_type 当成仅有 string/number/array 的 JSON 原生类型名。

## 6. 命令与执行结果：三个已复现问题

| 问题 | 本地诊断结果 | 对 Agent 的影响 | 建议 |
| --- | --- | --- | --- |
| 旧 search 业务失败仍无执行 error | mock HTTP 200、code=110000、success=false，App.Run 返回 nil | 新字段发现失败退出，后续 search 却可能被脚本判为成功 | user 搜索复用业务 envelope 校验；核对 app 兼容性 |
| 搜索请求数值变化 | 9007199254740993 在发送前变为 9007199254740992 | 即使模型原样填值，传到接口的数值也可能不同 | 请求 JSON 使用保真解码；不是让模型把所有数字都改字符串 |
| ID 类型 flag 无效 | 传 union_id，实际 query 仍为 user_id | help、Skill、实际请求不一致 | 修复映射或明确拒绝不支持的值，不能静默忽略 |

证据位置：[search 命令](../internal/cli/contract_command.go) 第 98/126 行、[共享 JSON 解析](../internal/cli/command_support.go) 第 306–326 行、[query 合并](../internal/openplatform/client.go) 第 498–514 行。

数值问题是 CLI 请求路径的 mock 复现，不是断言上述大数作为任意业务字段都被服务端接受。修复共享解析会影响合同创建、模板实例化、审批任务查询等调用方，需要覆盖这些既有输入。

此外，search --help 没有引导 search-fields，通用 user-id-type 说明与 user 搜索实际行为冲突；两条命令省略 --as 时的默认身份也不同。应同步帮助并持续显式携带 --as user，不应为简化一个场景擅自破坏 app 的默认兼容行为。

## 7. 结果说明与恢复

已有 has_more/token、页大小不等于总量、权限范围、无命中不代表系统不存在、命中片段不编造等规则应保留。建议统一结果摘要为：实际范围和全部条件、返回条目数、是否有后续页、是否获得服务端总数。

只在有证据时说明命中原因；缺少状态展示名称或命中片段时不补造。合同组数量和合同条目数量继续区分。字段发现零匹配、搜索零命中、鉴权失败、业务失败、条件不支持应成为不同的处理分支，不能全部以“没找到”结束。

新增条件、改变排序/范围与继续原查询分页应明确分开。前者重置 token，后者保持完整请求不变。没有可靠原请求时只询问缺失条件，不要求用户重复已知信息。

## 8. 验证方式与建议优先级

现有测试能验证 JSON 合法、字段选择、scope 和分页请求保持一致；这些不等价于服务端执行全部条件。保留这些测试，再补：元数据响应→完整请求转换、组合结果集、无候选条件不能变宽、修改查询重置分页、边界金额/日期、业务失败传播、ID/数值保真。用断言业务语义替代不必要的固定案例数量/文案约束。

| 顺序 | 工作 | 产出 |
| --- | --- | --- |
| 第一批 | 组合正确性、旧 search 错误信号、数值/ID 类型问题 | 可验证的执行边界与回归测试 |
| 第二批 | 字段类型冲突、部门角色、金额/日期边界、完整元数据转换案例 | 唯一且一致的字段契约 |
| 第三批 | 主文件决策入口、组合/追加/修改查询场景、help 联动、复用规则 | 更少猜测、重复查询和不必要追问 |

本次不需要继续扩充人员/部门等命令才能完成所有文档整理；但复杂组合的可靠实现必须先确认，不能仅靠场景文案宣称支持。
