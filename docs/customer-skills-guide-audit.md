## 修订思路

原文已有安装、授权、命令表和业务示例，但能力地图及身份说明落后于当前 Release。按用户进一步明确的结构，用户场景与能力地图均以 skill 为组织单位：15 个面向用户的 skill 各提供 1～2 个代表场景，共 24 个（不单独展示内部共享 skill）；能力地图沿用相同顺序并列明对应场景、完整能力范围和身份。保留身份表及必要命令，避免多份能力表重复。

证据优先级为：Release tag 下的实际命令与实现、该 tag 内置 skill 及配套参考、已有回归测试。不能把本机其他分支或全局安装的旧 skills 描述作为当前 Release 的能力范围，也不能把 CLI 有命令但 skill 明确禁止的流程宣传为可由 Agent 执行。

## 特别核验的能力边界

1. **搜索**：页面默认“全部”为十二字段同词 OR；页面文本为五类文本来源。申请人、需求人和部门角色不能互换；我方主体精确 ID 筛选无通用已验证配方。组展开与命中条目口径不同。依据：搜索 skill 总纲及 `references/search-combinations.md`。
2. **审查**：user-only；单文件 DOC/DOCX/PDF，本地文件和原始 stdin 上限 50 MiB；系统新发起需核实正文来源和状态。系统任务续查保留真实 businessId。外部预审没有系统详情页。依据：`contract-cli-review/SKILL.md` 的状态准入、文件准备及任务恢复章节。
3. **审查配置**：代码虽注册 batch 命令，skill 不允许执行批量配置。规则属于分组，清单引用规则；调整清单规则集合与跨分组迁移不同。不能用多次写入模拟原子删除/迁移。
4. **审批**：详情 user/app；个人评论和任务 user-only；拒绝意见必填，盖章及归档节点不由该任务接口办理。审批任务 ID、流程实例 ID 和 AI 审查任务 ID 不混用。
5. **文件**：“全部下载”由 Agent 编排，非独立命令。归档主文件归属不明、流程读取失败等必须说明材料缺口。
6. **交易方**：个人创建/局部更新不发起审批；不能写编码、风险、系统字段，启停独立操作；附件使用已有主数据文件。法人主体写入仍为 app。
7. **矩阵**：最多 2000 行，总列 12（条件＋结果最多 10）；计划有效期 24 小时，绑定身份与数据快照；逐行执行，取消不回滚。当前无法保证完整矩阵原样复制，可见信息重建需补齐并确认缺失配置。
8. **集成**：付款能力管理申请、计划和记录，不执行银行划款；签署链接不等于代签；出口 IP 查询不等于修改白名单；固定汇率不等于实时行情。
9. **发布范围**：共 16 个内置 skills，`api call` 未开放。本机未纳入该 Release 的到期提醒、我的草稿、我的协作、签署排行等目录不算发布能力。

## 版本核对注意

该 tag 中 `package.json` 的源码版本仍写为 `1.9.2-beta.1`；GitHub Release 为 v1.9.5，两者不能混作同一个证据。Go 二进制发布版本通过构建参数注入；未注入的本地验证构建显示 `dev`，不表示切到了 dev 业务环境。本次以 tag/commit、嵌入文件和命令实现为能力基线，没有改写包版本，也没有据此宣称 npm 已发布相同版本。

`skills list` 展示构建版本；`skills install` 会把该版本写入安装后的 SKILL.md。源码 skill 的独立 frontmatter 版本不能直接拿来验证安装结果。正文保留 `@latest` 作为升级入口，并说明实际版本不同于文稿时须重新核对。
